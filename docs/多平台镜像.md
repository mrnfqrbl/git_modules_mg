# 多平台镜像目标(未实现 / 设计备忘)

当前实现只把 GitHub 仓库镜像到 Gitee。未来需要支持同时镜像到 openi、Gitee、内网 Gitea 等。这里记录一次设计思路,后续实现参考即可,不作为当前版本的交付范围。

## 一、总体思路

把"目标平台"抽象成**目标端列表**而不是单一平台。一次迁移流程对每条清单条目:

- 解析一次 GitHub 源(clone + 递归分析依赖/子模块)
- 依次镜像到每一个目标端
- 在根仓库写回时,按**首选目标端**更新 URL;其余目标端作为"备份镜像"保留在溯源记录里

## 二、落地方式

1. `lib/git_base_api.py` 已经有 `GitBaseApi` 抽象基类,`GitHubApi` / `GiteeApi` 是实现。新增目标只需继承:
   - `OpeniApi`(https://openi.pcl.ac.cn)
   - `GiteaApi`(自建,url 走 config)
   - `GitlabApi` 等
2. `lib/main_api.py` 的 `支持的平台` 改成可插拔表,`平台变量映射` 同步扩展。
3. `lib/子仓库管理.py` 的 `根仓库管理器` 增加 `镜像目标列表`(按优先级排序),`处理` 循环对每个目标端都跑一遍"创建仓库 + push + 设公开"。

## 三、关键注意点

1. **唯一仓库名冲突**:每个平台独立判重,不要用同一个 `_N` 序号,避免出现 A 平台用 `xxx_1`、B 平台用 `xxx`,后续对账对不上。建议把**首选平台生成的最终名**作为其他平台的基础名,各平台再独立判重。
2. **各平台 API 差异**:
   - Gitee:`public` / `private` 两套字段都存在,创建和修改行为不对称(创建走 `public` 数字,修改走 `private` 数字)。
   - openi(Gogs 系):更接近 GitHub,字段 `private: bool`。
   - Gitea:和 openi 基本一致,但多出"组织"维度。
3. **空仓库可见性**:Gitee 不允许空仓库公开,必须"推送后再改公开";openi/Gitea 通常没这个限制。这条逻辑目前挂在 Gitee 分支里,抽象层加一个钩子 `需要推送后再公开(): bool`,由各平台实现。
4. **SSH vs HTTPS**:目前 push 用的是 HTTPS + Token。多平台情况下建议统一 HTTPS + Token,不引入 SSH,避免凭据管理复杂度。
5. **速率限制**:多目标端意味着同一份数据要 push 多次,Gitee 对免费账号有频率限制(QPS 很低),串行处理即可,不要并发。
6. **溯源文件格式**:`submod_data.json` 的 `当前` 字段要升级成数组或字典,记录每个镜像的 url + 新提交哈希:
   ```json
   {
     "当前": {
       "首选平台": "gitee",
       "镜像": {
         "gitee":   {"url": "...", "hash": "..."},
         "openi":   {"url": "...", "hash": "..."}
       }
     }
   }
   ```
7. **全局映射表**(`~/.git_modules_mg/migration_map.json`)key 需要带平台标识:`github_url@hash@平台`,避免跨平台串映射。
8. **失败回滚**:某个目标端失败不能阻塞其他目标端,但一定要在溯源里标记"部分失败",在 `run` 的结束报告里高亮,否则后续排查困难。
9. **Token 输入**:`config.ini` 和环境变量都要同步支持新平台;在 `main_api` 的 `初始化单个平台` 里加循环即可。

## 四、要避的坑

- 不要把"平台"字符串硬编码进 `仓库任务`/`根仓库管理器`,统一通过 `平台适配器` 对象操作(创建仓库、设公开、是否需要延迟公开)。
- 写入 `.gitmodules` 的时候不要写 token。URL 应该永远是公开形态,push 时再在 remote URL 里拼 `oauth2:<token>@`。
- 迁移任务缓存目录按 `(github_url, 提交哈希)` 做 key,而不是 `(github_url, 提交哈希, 平台)`;同一份源码对多目标可以复用本地克隆。
